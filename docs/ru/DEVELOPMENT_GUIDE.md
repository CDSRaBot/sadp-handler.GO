# Руководство по циклу разработки
## Проект: SADP-handler
## Язык: Go
## Версия: 1.0.0

Этот документ устанавливает обязательный порядок работ по расширению или изменению системы на Go. Основной принцип: **«Проектирование важнее кода»**.

## Основные инструменты
- рабочий репозиторий https://github.com/CDSRaBot/sadp-handler.GO/
- рабочая папка C:\Git\sadp-handler.GO\sadp-handler.GO\
- для работы с репозиториями github использовать неинтерактивные методы:
  - Первый выбор: GitHub MCP Server в VSCode
  - Второй выбор - если первый неддоступен: консольную утилиту `gh`, она установлена и доступна в powershell и windows terminal; проверка доступности: `gh -version`; авторизация - через web; список команд: `gh -help`
- для сборки, проверки и запуска программ на go использовать `go`, версия 1.27+; список команд - `go help`
- для обновления информации по пакетам go использовать поиск через mcp Context7 в VSCode

## Фаза 1: Определение задачи

Каждая функция начинается с чёткого описания цели и технического контракта.
- **Результат**: определены границы ответственности, поведение, внешний API и допустимые входные и выходные данные.
- **Для Go фиксируются**:
  - пакеты и публичные функции;
  - типы данных и структуры;
  - ожидаемые ошибки и их значения;
  - контракт взаимодействия с сетью, XML, HTTP, UDP, файлами и CLI.

## Фаза 2: Декомпозиция (спецификация сверху вниз)

Движение от общего к частному по уровням:
1. **Уровень системы (`SYSTEM.md`)**:
   - регистрация нового модуля;
   - описание его роли в приложении;
   - границы ответственности и зависимостей.
2. **Уровень пакета (`internal/...`, `pkg/...`)**:
   - назначение пакета;
   - публичный API;
   - входные и выходные структуры;
   - ограничения производительности и правила обработки ошибок.
3. **Уровень функции или метода (`procedures/*.md`)**:
   - атомарное описание логики;
   - обязательный контракт:
     - входные параметры;
     - возвращаемые значения;
     - типы ошибок;
     - поведение при `nil`, пустых данных и тайм-аутах;
   - обязательное описание исключений и политики `errors` / `panic`.

## Фаза 3: Рекурсивный аудит спецификаций

Перед написанием кода проверяется целостность документации:
- **Цепочка данных**: результат функции N должен полностью удовлетворять требованиям к входу функции N+1.
- **Модель ошибок**: каждый возможный сбой описан и обработан.
- **Кроссплатформенность**: все системные вызовы, сетевые операции и пути к файлам должны поддерживаться целевыми ОС.
- **Особенности Go**:
  - корректность типов (`struct`, `interface`, `error`);
  - корректность использования `context.Context`;
  - корректность сериализации и десериализации JSON/XML;
  - корректность схем с `goroutine` и `channel`, если используется параллелизм.

## Фаза 4: Написание тестов (разработка через тестирование)

Тесты на основе спецификаций создаются до написания кода. Для проверки тестов используется заглушка функции, возвращающая ошибку `errors.New("not implemented")`. Реализация функции пишется только после того, как все тесты станут красными.

### Создание Issues

В самом начале работы по Фазе 4 производится разбиение на задачи. Задачи сохраняются в Issues репозитория https://github.com/CDSRaBot/sadp-handler.GO 

**Для каждой задачи дается контекст**, включающий:
- раздел **Фаза 4: Написание тестов (разработка через тестирование)**, стр. 53-88
- ссылка на файл спецификации, по которой производится создание задачи
- Инструменты и окружение
- Входные данные и тестовые сценарии (позитивные и негативные, безопасность)
- Выходные артефакты (Файл тестов: internal/logic/*_test.go, Заглушка сигнатуры (при необходимости): internal/logic/name_of_procedure.go)
- Критерии приемки

- **Контрактные тесты**:
  - проверка типов данных;
  - проверка структур и полей;
  - проверка возвращаемых ошибок.
- **Логические тесты**:
  - проверка алгоритмов на эталонных данных;
  - проверка разбора XML/JSON;
  - проверка сетевых сценариев.
- **Негативные тесты**:
  - обработка пустого ввода;
  - неверный XML;
  - неполные структуры;
  - тайм-ауты;
  - данные в некорректном формате;
  - фаззинг строк и двоичных данных.
- **Стиль Go**:
  - тесты размещаются в файлах `*_test.go`;
  - используются `testing` и `t.Run`;
  - ошибки проверяются через `require`/`assert` или стандартный пакет `testing`.

После завершения разработки тестов выполняются процедуры, описанные в **Фаза 7** (Статический анализ и контроль качества) и **Фаза 8** (Сборка, выпуск и версионирование), что гарантирует поддержание кода в надлежащем состоянии.

### Критерии приемки

Во время Фазы 4 все тесты **должны быть красными**. 

## Фаза 5: Реализация (снизу вверх)

Код пишется от небольших атомарных функций к точкам входа.
- При разработке соблюдать правила Go:
  - корректные имена пакетов;
  - понятные имена функций;
  - отсутствие глобального состояния без необходимости;
  - явная обработка ошибок;
  - использование `context.Context` в сетевых операциях и операциях ввода-вывода.
- **Правила документирования**:
  - комментарии и docstring — на английском языке;
  - публичные функции и типы должны быть описаны;
  - комментарии добавляются только там, где они действительно помогают.
- **Обязательные правила**:
  - не использовать `panic` в производственной логике;
  - не игнорировать `error`;
  - не собирать XML/JSON через `fmt.Sprintf`, если для этого подходит сериализатор;
  - не допускать утечек горутин;
  - закрывать ресурсы: `defer file.Close()`, `defer resp.Body.Close()`.

## Фаза 6: Рекурсивная проверка кода

Проверка соответствия кода спецификации:
1. **Модульная проверка**: для каждой функции успешно проходят соответствующие тесты.
2. **Проверка цепочки**: проверяется корректность преобразования данных между пакетами и уровнями приложения.
3. **Интеграционная проверка**: проверяется взаимодействие с сетью, XML, HTTP, устройствами и файлами.
4. **Рефакторинг**: если при реализации пришлось изменить логику, вернуться к фазе 2 и обновить спецификацию.

## Фаза 7: Статический анализ и контроль качества

Запустить инструменты контроля качества:
- `gofmt -w .` — форматирование кода;
- `go vet ./...` — поиск типичных ошибок Go;
- `staticcheck ./...` — статический анализ;
- `golangci-lint run` — комплексная проверка качества;
- `go test ./...` — запуск всех тестов;
- `go mod tidy` — актуализация зависимостей;
- `go build ./...` — проверка сборки проекта.

## Фаза 8: Сборка, выпуск и версионирование

1. **Тестирование**:
   - все модульные и интеграционные тесты проходят успешно;
   - проект собирается без ошибок.
2. **Коммит**:
   - зафиксировать изменения;
   - подробно описать их в сообщении коммита.
3. **Тег**:
   - создать Git-тег версии проекта;
   - предпочтительный формат — `vX.Y.Z`.
4. **Отправка**:
   - синхронизировать изменения с удалённым репозиторием.
5. **Релиз**:
   - подготовить журнал изменений;
   - при необходимости оформить релиз и бинарные сборки.

## Фаза 9: Архитектурные правила Go-проекта

Для всех изменений в проекте соблюдать следующие принципы:
- **`cmd/`** — точки входа приложения;
- **`internal/`** — бизнес-логика и приватные компоненты;
- **`pkg/`** — библиотеки повторного использования, которые могут быть вынесены за пределы проекта;
- **`config/`** — параметры конфигурации;
- **`models/`** — структуры данных;
- **`utils/`** — вспомогательные функции;
- **`docs/`** — документация и спецификации.
- Не смешивать уровни ответственности.
- Не использовать глобальные переменные без крайней необходимости.
- Использовать интерфейсы там, где нужны тестируемость или возможность замены зависимостей.
- Размещать работу с устройствами, XML и сетью в отдельных пакетах.

## Фаза 10: Политика ошибок и безопасности

- Все ошибки должны быть явными и доступными для проверки.
- Не использовать `panic` в рабочем коде, за исключением `main` и чётко ограниченных сценариев.
- Сетевые запросы должны иметь тайм-ауты.
- XML/JSON необходимо проверять и корректно обрабатывать.
- Ограничивать размер входных данных и потребление ресурсов.
- Не доверять входным данным без проверки.
