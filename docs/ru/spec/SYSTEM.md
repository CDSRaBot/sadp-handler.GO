# Системная спецификация: SADP-handler (v0.1.0)

## 1. Назначение и статус

**SADP-handler** — терминальная утилита на Go для обнаружения, активации и настройки камер и NVR Hikvision по протоколу Search Active Device Protocol (SADP). Обнаружение выполняется в локальной сети уровня 2, включая устройства без адреса, доступного хосту.

Архитектурная основа определена; спецификации задают границы системы, API модулей и атомарные процедуры. Реализация на Python является проверенной поведенческой базой обнаружения: она проверена на реальных устройствах, находит их и получает от них ответы. Реализация на Go должна сохранить это поведение и пройти проверку в том же сценарии с реальными устройствами. Для активации SADP-запрос адресуется по MAC и формируется согласно M3. Расчёт «запрос-ответ challenge-response» `SHA-256(UTF-8(password + challenge))` принят как подтверждённый практическими экспериментами. Сквозные операции на Go ещё требуют реализации и интеграционных тестов; детали, не подтверждённые экспериментами, остаются открытыми.

## 2. Функциональный охват

Система проектируется для следующих возможностей:

1. **Обнаружение устройств** — отправлять SADP inquiry-probe и принимать ответы устройств через поддерживаемые локальные сетевые интерфейсы. Реализация на Python проверена на реальных устройствах: она находит устройства и получает от них ответы; её поведение является базой совместимости для реализации на Go. Перехваты HiToolsDelivery документируют совместимый трафик: multicast-назначение UDP `239.255.255.250:37020`, XML-запрос `<Probe>` с элементами `<Uuid>`, `<Types>inquiry</Types>` и `<ResponseMode>2</ResponseMode>`, сообщения `<ProbeMatch>` и отдельное multicast-сообщение `<Hello>` с `<Types>hello</Types>`. Перехваты не устанавливают универсальные правила корреляции ответов, повторы, временные интервалы или поведение всех моделей и прошивок.
2. **Активация устройств** — отправлять SADP XML-запрос активации, адресованный по MAC целевого устройства, соблюдая правила сложности пароля. Формат запроса, подтверждённый практическими экспериментами, является базой совместимости; обработка результата активации остаётся частью рабочего процесса приложения.
3. **Настройка сети** — задавать IP-адрес устройства, маску подсети, шлюз и состояние DHCP.
4. **Работа через CLI** — предоставлять пользователям и средствам автоматизации доступ к этим сценариям через общий каталог команд и типизированные результаты. Режим интерфейса по умолчанию — полноэкранный TUI; `--ui=no` запускает интерактивный CLI REPL, а `--ui=no --once` выполняет одну команду из аргументов процесса и завершает его.

Это целевые возможности, а не утверждение о том, что сквозные операции с устройствами уже реализованы. При пакетной активации и настройке сети необходимо сообщать результат для каждого устройства отдельно, чтобы сбой одного устройства не скрывал результаты остальных. M3 определяет SADP-запрос активации; до включения команд требуется завершить сквозную отправку/обработку результата активации и транспорт/обработку результата настройки сети.

## 3. Границы модулей

Модули взаимодействуют через API Go-пакетов и явно заданные типы Go. Пакет владеет своими данными и ошибками; вызывающий код не должен зависеть от закрытой реализации другого пакета.

### [M0: Адаптер платформы](./modules/adapter.md)

**Роль:** изолировать различия операционных систем и сетевых интерфейсов.

- Перечислять подходящие интерфейсы и предоставлять адресные и аппаратные сведения, необходимые SADP.
- Настраивать и обслуживать сокеты для SADP-трафика на выбранном интерфейсе.
- Изолировать платформозависимое поведение небольшой интерфейсной или пакетной границей там, где это улучшает переносимость и тестируемость.

### [M1: Сетевое ядро](./modules/network.md)

**Роль:** управлять отправкой SADP UDP-probe и жизненным циклом приёма.

- Формировать и отправлять наблюдаемый inquiry-probe через multicast-соединение, настроенное M0, и принимать объявления средствами сетевых API Go из `net`.
- Отделять подтверждённый контракт запроса probe от неподтверждённых правил ответа, корреляции, повторов и времени ожидания.
- Использовать горутины и каналы только при необходимости; явно задавать остановку и отмену listener.
- Принимать `context.Context` для блокирующих операций и обеспечивать освобождение сокетов, горутин и других ресурсов при завершении или отмене.
- Передавать принятые данные парсеру, не помещая бизнес-правила в транспортный слой.

### [M2: Парсер данных](./modules/parser.md)

**Роль:** проверять и преобразовывать недоверенные данные устройств.

- Разбирать SADP XML стандартным пакетом Go `encoding/xml`.
- Преобразовывать корректные объявления в типизированные модели Go, используемые остальными компонентами приложения.
- Проверять обязательные поля и ограничивать размер входных данных и значения до передачи бизнес-логике.
- Возвращать явные ошибки для некорректных или неполных данных; неизвестные необязательные поля можно игнорировать, если это сохраняет совместимость с будущими версиями.

### [M3: Логика устройств](./modules/logic.md)

**Роль:** реализовывать правила и рабочие процессы управления устройствами.

- Координировать активацию, обмен challenge-response и настройку сети.
- Проверять пароли и конфигурацию до отправки команд.
- Формировать протокольные данные из проверенных типизированных значений и интерпретировать ответы устройств.
- Не связывать правила рабочих процессов с представлением CLI или деталями операционной системы.

### [M4: Интерфейс командной строки](./modules/ui.md)

**Роль:** предоставлять пользовательский интерфейс командной строки и связывать проверенные запросы пользователя с рабочими процессами приложения.

- Разбирать и проверять аргументы командной строки и конфигурацию.
- Показывать результаты обнаружения и операций, включая ошибки и частичные результаты.
- По умолчанию запускать TUI; выбирать обычный режим командной строки только при `--ui=no`. Если для TUI недоступны пригодные терминальные потоки ввода и вывода, сообщать понятную ошибку.
- Отделять взаимодействие с терминалом от бизнес-логики; не делать конкретную библиотеку CLI обязательной на системном уровне.
- Использовать отдельные парсеры TUI и CLI, которые преобразуют ввод в общую типизированную модель команды и диспетчер. `--ui=no` выбирает REPL, а `--once` — однократное выполнение.

### [M5: Локализация](./modules/localization.md)

**Роль:** проверять, загружать, разрешать и переключать неизменяемые каталоги локалей независимо от отображения терминала.

- Использовать встроенный английский каталог как канонический набор ключей и fallback.
- Перечислять внешние файлы локалей и экспортировать английский шаблон для перевода.
- Устанавливать полностью загруженную локаль одним атомарным изменением состояния; неудачная загрузка не меняет текущую локаль.

M5 предоставляет службы локализации модулю M4 и не отвечает за разбор командной строки или представление в терминале.

### [M6: Координатор обнаружения](./modules/discovery.md)

**Роль:** объединять настройку сокета для выбранного интерфейса, запланированные отправки наблюдаемого inquiry-probe, приём датаграмм и разбор объявлений в один отменяемый сеанс обнаружения.

- За один вызов работать на одном явно выбранном интерфейсе и передавать вызывающему обработчику разобранные устройства или отклонённые датаграммы.
- Явно задавать владение сокетом, отмену, ошибки callback и частичные результаты.
- Не выводить корреляцию ответов или требования протокола к повторам из расписания probe приложения и не назначать расписание незапрошенным сообщениям `Hello`.

M6 зависит от M0, M1 и M2; M4 вызывает M6 и отображает его события.

### [M7: Конфигурация](./modules/configuration.md)

**Роль:** загружать и проверять внешний `settings.json`.

- `settings.json` является единственным внешним источником базовых настроек.
- Для каждого ключа требуется запись в `_comments` с вариантами и границами
  значений.
- CLI-переопределения применяются после файла настроек и до запуска операций.

### [M8: Компоновка приложения](./modules/application.md)

**Роль:** преобразовывать настройки M7 в типизированный `RuntimeConfig` и
собирать зависимости M4, M5 и M6.

- Создавать `fs.FS` для M5, `MulticastOptions` для M0 и `DiscoveryOptions`
  для M6.
- Настраивать уровень `slog` из `logging.level`.
- Не допускать чтения `settings.json` протокольными и presentation-модулями.

### Политика логирования

Логирование является сквозной ответственностью, описанной в
[спецификации логирования](./logging.md), и реализуется стандартным пакетом
Go `log/slog`. M8 инициализирует один логгер до запуска workflow и передаёт
его модулям через типизированные зависимости. Логи записываются в `.\logs`,
файл ротируется до превышения 5 МиБ, а перед первой записью каждого запуска
процесса добавляются пустая строка и заголовок с датой и временем начала.
Каждый модуль и каждая атомарная процедура обязаны указать импорты, точки,
уровни, безопасные атрибуты, правила редакции и владельца событий по
спецификации логирования.

## 4. Контракты данных и API

- Публичные API пакетов используют типизированные значения Go, а не неструктурированные карты.
- Спецификация каждого пакета должна определять его назначение, публичный API, типы входных и выходных данных, возможные ошибки и поведение для nil- или пустых входов, тайм-аутов и отмены, если это применимо.
- Данные между модулями проверяются на границе входа в систему. Необработанные сетевые данные нельзя считать доверенными моделями приложения.
- Ошибки являются частью контракта каждого API. Вызывающий код должен иметь возможность различать ошибки и оборачивать их контекстом; некорректные данные и неудачные операции нельзя представлять успешными нулевыми значениями.
- Если вызывающий код ветвится по категории отказа, пакет должен предоставлять типизированную ошибку или sentinel и сохранять её при оборачивании через `Unwrap`; вызывающий код использует `errors.Is`/`errors.As`, а не разбирает текст ошибки. Контракт задаёт стабильные категории и сохранение исходной причины.
- Использовать интерфейсы на границах зависимостей, когда подмена нужна для тестирования или переносимости. Не вводить интерфейсы или глобальное состояние без конкретной необходимости.

## 5. Архитектура Go и ограничения среды выполнения

- Целевая версия — **Go 1.22 или новее**, согласно README проекта.
- Путь Go-модуля — `github.com/CDSRaBot/sadp-handler.GO`, соответствующий планируемому репозиторию GitHub. Импорты Go начинаются с этого пути.
- Соблюдать структуру проекта: `cmd/` для точек входа исполняемых файлов, `internal/` для приложения и закрытой реализации, `pkg/` только для библиотек, намеренно предназначенных для повторного использования вне этого модуля. Создавать `config/`, `models/` или `utils/` только при наличии чёткой ответственности соответствующего пакета.
- Пути файловой системы репозитория в документации, конфигурации и инструкциях по сборке задаются относительно корня проекта. Не задавать абсолютные пути, зависящие от конкретной машины.
- Размещать перечисление интерфейсов и настройку сокетов в адаптере платформы, транспорт — в сетевом ядре, разбор данных — в парсере, рабочие процессы устройств — в логике, представление — в CLI.
- Оставлять оркестрацию обнаружения в M6, а управление каталогами/состоянием локалей — в M5; ни то ни другое не относится к модулю представления CLI.
- Использовать `context.Context` для отменяемых сетевых операций и операций ввода-вывода. Для параллельных задач задавать владельца, путь остановки и стратегию передачи ошибок; не допускать утечек горутин и неограниченного использования ресурсов.
- Сохранять режим интерфейса неизменным в рамках одного запуска процесса. Команды приложения в TUI запускают рабочие процессы внутри TUI; переход в стандартный CLI требует отдельного запуска.
- В режиме CLI использовать REPL, если явно не указан `--once`; не определять однократное выполнение только по наличию аргументов команды.
- TUI управляет не более чем одним непрерывным сеансом обнаружения. При смене интерфейса остановить и завершить прежний сеанс до запуска нового.
- Предпочитать стандартную библиотеку Go, включая `net`, `encoding/xml`, `context` и `log/slog`. При реализации можно выбрать зависимость для CLI, конфигурации или журналирования, но системная спецификация не требует сторонних библиотек.
- Комментарии в исходном коде и документация публичных элементов Go пишутся на английском языке. Документировать экспортируемые типы и функции; комментарии реализации добавлять только для пояснения неочевидного поведения.

## 6. Политика обработки ошибок, безопасности и ресурсов

- Явно возвращать ошибки и обрабатывать их. Не игнорировать ошибки и не использовать `panic` в производственных рабочих процессах.
- Применять тайм-ауты или отмену к сетевым операциям; ограничивать размер входных данных, параллелизм и потребление других ресурсов.
- Считать сетевые данные, ввод CLI и конфигурацию недоверенными. До использования проверять адреса, порты, поля устройств, пароли и значения протокола.
- Все базовые настройки читаются через M7 из `settings.json`. Полный список,
  defaults, комментарии и границы приведены в [M7](./modules/configuration.md)
  и шаблоне [`settings.json`](../../../settings.json). В частности,
  `network.max_sadp_datagram_size` по умолчанию равен 1500 байт (ноль также
  означает default), допустимый диапазон — `1..65507`; передавать одно
  разрешённое значение через обнаружение в M1 и M2. Это прикладное ограничение
  ресурсов, а не максимум SADP.
- Разбирать XML с помощью `encoding/xml`; не собирать XML или JSON форматированием строк, если для этого подходит сериализатор.
- Не журналировать пароли, производные от паролей секреты и другие чувствительные данные активации.
- Не журналировать полные сетевые payload, XML или полные документы
  конфигурации. Диагностический журнал должен быть отделён от text/JSON
  вывода CLI.
- Закрывать файлы, тела ответов, сокеты и другие принадлежащие приложению ресурсы на всех соответствующих путях выполнения.

## 7. Требования к спецификациям и проверке

Изменения выполняются согласно жизненному циклу разработки в [`DEVELOPMENT_GUIDE.md`](../DEVELOPMENT_GUIDE.md):

1. До реализации определить поведение, границы пакетов, типы Go и контракт ошибок.
2. При изменении ответственности или зависимостей модулей обновлять этот системный документ; описывать API пакетов и атомарные процедуры на соответствующих уровнях.
3. Если русский документ ссылается на контракт на английском, английский документ является нормативным источником; русская копия служит руководством и не должна ему противоречить.
4. До написания кода проверять поток данных, обработку ошибок, поддержку платформ, сериализацию, использование контекста и параллелизм.
5. Выводить тесты из спецификации, включая контрактные, успешные и негативные сценарии, тайм-ауты и фаззинг, где это уместно. Файлы Go-тестов должны иметь суффикс `*_test.go`; использовать стандартный пакет `testing`.
6. Проверять реализацию применимыми проверками проекта, включая `gofmt`, `go vet ./...`, `go test ./...` и `go build ./...`. При наличии настроенных инструментов запускать также `staticcheck` или `golangci-lint`.
7. Если реализация меняет описанное поведение, одновременно обновлять спецификацию и тесты.

## 8. Референс на Python и условия совместимости протокола

Пользователь указал `../examples/SADP-app` как работающую реализацию на Python и поручил использовать её подход к обработке как локальный поведенческий референс. Реализация использует UDP-сокеты с выбором интерфейса, передаёт полученные датаграммы с адресом отправителя и временем приёма, разбирает XML в типизированную модель устройства и вычисляет `SHA-256(UTF-8(password + challenge))` в виде шестнадцатеричной строки нижнего регистра.

Это референс реализации, а не авторитетная спецификация протокола SADP. Отдельные компоненты Python описывают лишь части сетевого обмена, однако полная реализация обнаружения, как отмечено выше, проверена на реальных устройствах. Приведённые ниже сведения о компонентах описывают детали реализации и не ограничивают эти сквозные подтверждения:

- `core/contracts.py` задаёт `239.255.255.250:37020` и `MAX_PACKET_SIZE = 1500`. В этом коде размер обозначен как ограничение для fuzzing/MTU; это не подтверждённый максимальный размер SADP-пакета.
- `core/adapter.py` в Unix-подобных системах присоединяется к multicast-группе через выбранный интерфейс, привязывает UDP/37020 и задаёт multicast TTL 64. Ветка Windows привязывает адрес интерфейса к эфемерному порту и не присоединяется к multicast-группе. Адаптер Go должен реализовывать и тестировать требуемое поведение выбранного интерфейса в каждой ОС, а не копировать это расхождение.
- `core/protocol.py` ограничивает размер принимаемых датаграмм и синхронно передаёт их callback. Рассматривать область этого файла отдельно от проверенного сквозного поведения обнаружения: успешная работа не устанавливает универсальные правила корреляции ответов или повторов.
- `services/parser.py` ожидает непосредственные дочерние XML-поля `MAC`, `IPv4Address`, `Activated`, `DeviceModel`, `SerialNumber` и необязательное `SoftwareVersion`. Парсер принимает UTF-8 с fallback на ISO-8859-1, требует MAC и IPv4-адрес и использует `defusedxml`.
- `services/logic/crypto.py` вычисляет SHA-256 от байтов UTF-8 строки `password + challenge`. Вспомогательная функция извлечения полей `Challenge`/`Salt` сама по себе не реализует согласование challenge.
- `services/logic/__init__.py` формирует XML-запросы `Activate` и `NetworkParameter`. В ветке без challenge отправляется пароль в открытом виде; данная спецификация Go явно не принимает этот fallback.

Успешное обнаружение реальными устройствами в реализации Python является проверенным поведением и базой для этой функции, но само по себе не гарантирует универсальность протокола. Следующие детали протокола остаются открытыми, пока не проверены отдельно:

- Предоставленные пользователем перехваты HiToolsDelivery показывают запросы к UDP multicast `239.255.255.250:37020` с XML-элементами `Probe`: `Uuid`, `Types=inquiry` и `ResponseMode=2`. Двенадцать записей запросов содержат шесть значений UUID, каждое встречается дважды; это наблюдение, а не требование повторной отправки.
- В последующем перехвате есть XML-ответ `ProbeMatch` размером 1 382 байта для DS-2CD1021-I. Его непосредственные дочерние поля включают `Uuid`, `Types=inquiry`, описание устройства и серийный номер, порты команд/HTTP, сетевые поля MAC и IPv4/IPv6, DHCP и число каналов, версии ПО/DSP, время загрузки, поля активации/возможностей безопасности, `Salt` и поля блокировки/сброса. UUID ответа совпадает в двух показанных записях ответа. Соответствующий запрос в этом перехвате отсутствует, поэтому совпадение с UUID probe не подтверждено.
- В записи перехвата показан обмен между `192.168.0.128` и `192.168.0.160` по UDP/37020, а также датаграмма от устройства `192.168.0.160:37020` к `239.255.255.250:37020` с тем же отображённым содержимым `ProbeMatch`. Сохранять эти сведения как наблюдения и не делать выводов об универсальном поведении unicast/multicast-доставки.
- В другом перехвате содержатся четырнадцать XML-документов `Probe`: семь различных значений UUID, каждое встречается дважды в multicast-трафике к `239.255.255.250:37020`. Это согласуется с повторными передачами в данном перехвате, но не доказывает обязательность повторов, семантику пар, периодичность или необходимость повторного использования UUID.
- В том же позднем перехвате есть датаграмма UDP от устройства размером 1 319 байт, отправленная с `192.168.0.160:37020` на `239.255.255.250:37020`; её корневой элемент — `<Hello>`, тип — `<Types>hello</Types>`, а поля сведений об устройстве пересекаются с наблюдаемыми в `ProbeMatch`. В отображённом сообщении нет UUID; оно следует после показанной серии probe, но перехват не доказывает, что это ответ на данную серию, и не задаёт расписание объявления.
- Не сохранять примерные MAC-адреса, серийные номера, UUID или значения salt в спецификациях и тестовых наборах. Считать поля ответа, связанные с безопасностью, чувствительными и никогда не журналировать XML-ответ целиком.
- До того как делать поля обязательными или определять повторы, расписание либо универсальные гарантии доставки ответа, проверить варианты `ProbeMatch`/`Hello` и корреляцию на дополнительных устройствах и прошивках.
- Завершить контракт сквозной транспортной операции активации и настройки сети: поток/корреляцию ответов, тайм-аут, отмену и сопоставление результатов с устройствами. M1 P1.4 определяет отправку готовой SADP-датаграммы; передача запроса не означает, что обработка результата устройства уже реализована.
- Поля XML активации и адресация по MAC, а также расчёт «запрос-ответ challenge-response» `SHA-256(UTF-8(password + challenge))` для настройки сети приняты как подтверждённые практическими экспериментами и являются нормативным контрактом M3. Не считать их неподтверждёнными предложениями Python-референса.
- Значение по умолчанию `MaxSADPDatagramSize` равно 1500 байт и настраивается через настройки JSON. M1 и M2 используют одно общее разрешённое значение, а приёмник обнаруживает и отклоняет усечение и превышение размера.
- Продолжать проверку обработки результата активации и полного обмена настройки сети: подтверждение формата запроса и хеша не устанавливает семантику всех результатов устройств или поведение всех моделей/прошивок.
- Проверить UDP multicast через отдельные интерфейсы, а также отмену и очистку на каждой поддерживаемой ОС. В частности, не воспроизводить ветку Python для Windows без подтверждения получения требуемых ответов SADP.
- До реализации окончательно определить пути пакетов. Путь модуля задаётся в `go.mod`; сигнатуры API в документах модулей являются проектными контрактами, а не реализованными символами.

Реализация Go ещё не начата, поэтому соответствие Go-поведения проверенной базе обнаружения на Python предстоит реализовать и проверить. Открытые выше вопросы не отменяют подтверждённую работу Python-реализации; они ограничивают утверждения о непроверенных деталях протокола, других устройствах/платформах, активации и настройке сети.
