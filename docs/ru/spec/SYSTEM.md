# Системная спецификация: SADP-handler (v0.1.0)

## 1. Назначение и статус

**SADP-handler** — CLI-утилита на Go для обнаружения, активации и настройки устройств Hikvision по протоколу Search Active Device Protocol (SADP). Обнаружение выполняется в локальной сети уровня L2, в том числе для устройств без IP-адреса, доступного хосту.

Этап декомпозиции спецификаций определяет границы системы, модульные API и атомарные процедуры. Документация discovery и локализации синхронизирована; выполнение операций управления устройствами остаётся заблокированным до подтверждения протокола.

## 2. Функциональный охват

Система проектируется для предоставления следующих возможностей:

1. **Обнаружение устройств** — отправка наблюдаемого SADP inquiry-probe и получение объявлений через поддерживаемые локальные интерфейсы. Перехваты подтверждают multicast `239.255.255.250:37020`, запрос XML `<Probe>` (`Uuid`, `Types=inquiry`, `ResponseMode=2`), ответ `<ProbeMatch>` и отдельное объявление `<Hello>` (`Types=hello`). Полный контракт корреляции, повторов и времени ожидания пока не установлен.
2. **Активация устройств** — активация неактивных устройств с соблюдением требований к сложности пароля и необходимого механизма защиты.
3. **Настройка сети** — настройка IP-адреса, маски подсети, шлюза и режима DHCP устройства.
4. **Работа через CLI** — доступ к этим сценариям пользователям и автоматизированным системам с помощью структурированной конфигурации, вывода и журналирования. Режим по умолчанию для пользователя — полноэкранный TUI; `--ui=no` включает стандартный режим командной строки для разовых операций и автоматизации.

Это целевые возможности, а не утверждение, что сквозные операции с устройствами уже полностью описаны или реализованы. При пакетной активации и настройке сети необходимо сообщать результат для каждого устройства отдельно, чтобы сбой одного устройства не скрывал результаты остальных. Текущие контракты модулей ещё не определяют отправку этих запросов и полный цикл получения/сопоставления ответов.

## 3. Границы модулей

Модули взаимодействуют через API Go-пакетов и явно определённые типы Go. Каждый пакет отвечает за собственные данные и ошибки; вызывающий код не должен зависеть от закрытой реализации другого пакета.

### [M0: Адаптер платформы](./modules/adapter.md)

**Роль:** изолировать различия операционных систем и сетевых интерфейсов.

- Перечислять подходящие интерфейсы и предоставлять адресные и аппаратные атрибуты, необходимые SADP.
- Настраивать и владеть сокетами для обмена SADP-трафиком через выбранный интерфейс.
- Изолировать платформозависимое поведение небольшим интерфейсом или границей пакета, если это улучшает переносимость и тестируемость.

### [M1: Сетевое ядро](./modules/network.md)

**Роль:** отправлять наблюдаемый inquiry-probe SADP и управлять жизненным циклом приёма UDP.

- Формировать и отправлять подтверждённый перехватом inquiry-probe через multicast-соединение M0.
- Принимать объявления устройств с помощью сетевых API Go из `net`.
- Не выводить правила корреляции, повторов и периодичность из имеющихся перехватов.
- Использовать горутины и каналы только при необходимости; явно определять остановку и отмену прослушивателя.
- Принимать `context.Context` для блокирующих операций и освобождать сокеты, горутины и другие ресурсы после завершения или отмены.
- Передавать полученные данные парсеру, не внедряя в транспорт бизнес-правила.

### [M2: Парсер данных](./modules/parser.md)

**Роль:** проверять и преобразовывать недоверенные данные устройств.

- Разбирать SADP XML стандартным пакетом Go `encoding/xml`.
- Преобразовывать корректные объявления в типизированные модели Go для остальных частей приложения.
- Проверять обязательные поля и ограничивать размер входных данных и значения до передачи бизнес-логике.
- Возвращать явные ошибки при некорректном или неполном вводе; неизвестные необязательные поля можно игнорировать, если это обеспечивает совместимость с новыми версиями прошивок.

### [M3: Логика устройств](./modules/logic.md)

**Роль:** реализовывать правила управления устройствами и рабочие процессы.

- Координировать активацию, обмен «вызов — ответ» и настройку сетевых параметров.
- Проверять пароли и конфигурацию до отправки команд.
- Формировать протокольные сообщения из проверенных типизированных данных и интерпретировать ответы устройств.
- Не связывать правила рабочих процессов с отображением CLI и деталями операционной системы.

### [M4: Интерфейс командной строки](./modules/ui.md)

**Роль:** обеспечивать взаимодействие через командную строку и передавать пользовательские запросы рабочим процессам приложения.

- Разбирать и проверять аргументы командной строки и конфигурацию.
- Показывать результаты обнаружения и выполнения операций, включая ошибки и частичные результаты.
- Запускать TUI по умолчанию и выбирать стандартный режим командной строки только при наличии `--ui=no`; если для TUI нет доступных терминальных потоков ввода и вывода, сообщать понятную ошибку.
- Отделять взаимодействие с терминалом от бизнес-логики; на системном уровне не делать обязательной конкретную библиотеку CLI.

### [M5: Локализация](./modules/localization.md)

**Роль:** проверять, загружать, объединять и атомарно переключать каталоги локалей независимо от отображения терминала.

- Использовать встроенный английский каталог как канонический набор ключей и fallback.
- Перечислять внешние локали и экспортировать шаблон перевода.
- При ошибке загрузки не менять активное состояние локали.

### [M6: Координатор обнаружения](./modules/discovery.md)

**Роль:** объединять настройку сокета M0, отправку и приём UDP M1 и разбор объявлений M2 в один отменяемый сеанс на выбранном интерфейсе.

- Передавать вызывающему коду проверенные устройства и диагностические события отвергнутых датаграмм.
- Не повторять запрос и не сопоставлять UUID или unsolicited `Hello` без подтверждённых правил протокола.

M6 зависит от M0, M1 и M2; M4 вызывает его и отображает события.

## 4. Контракты данных и API

- В публичных API пакетов используются типизированные значения Go, а не неструктурированные карты.
- В спецификации каждого пакета должны быть указаны его назначение, публичный API, типы входных и выходных данных, возможные ошибки и поведение при `nil`, пустых данных, тайм-аутах и отмене, если это применимо.
- Данные проверяются на границе входа в систему. Необработанные сетевые данные нельзя считать доверенными моделями приложения.
- Ошибки являются частью контракта каждого API. Вызывающий код должен иметь возможность различать ошибки и оборачивать их контекстом; некорректные данные и сбои нельзя представлять как успешные нулевые значения.
- Использовать интерфейсы на границах зависимостей, если это необходимо для тестирования или переносимости. Не вводить интерфейсы и глобальное состояние без конкретной необходимости.

## 5. Архитектура и ограничения среды Go

- Целевая версия — **Go 1.22 или новее**, в соответствии с README проекта.
- Путь Go-модуля — `github.com/CDSRaBot/sadp-handler.GO`, в соответствии с планируемым репозиторием GitHub. Импорты Go начинаются с этого пути.
- Соблюдать структуру проекта: `cmd/` — точки входа исполняемых файлов, `internal/` — логика приложения и закрытые компоненты, `pkg/` — только библиотеки, предназначенные для повторного использования за пределами этого модуля. Добавлять каталоги `config/`, `models/` или `utils/` только при наличии чёткой ответственности пакета.
- Пути файловой системы репозитория в документации, конфигурации и инструкциях по сборке задаются относительно корня проекта. Не указывать абсолютные пути, зависящие от конкретной машины.
- Размещать перечисление интерфейсов и настройку сокетов в адаптере платформы, транспорт — в сетевом ядре, разбор данных — в парсере, рабочие процессы устройств — в логике, отображение — в CLI.
- Использовать `context.Context` для отменяемых сетевых операций и операций ввода-вывода. Для параллельных задач определить владельца, способ остановки и передачу ошибок; не допускать утечек горутин и неограниченного потребления ресурсов.
- Сохранять выбранный режим интерфейса в течение одного запуска процесса. Команды приложения из TUI запускают рабочие процессы внутри TUI; переход в стандартный режим CLI требует отдельного запуска программы.
- Предпочитать стандартную библиотеку Go, включая `net`, `encoding/xml`, `context` и `log/slog`. При реализации можно выбрать стороннюю библиотеку для CLI, конфигурации или журналирования, но системная спецификация не требует обязательных сторонних библиотек.
- Исходные комментарии и документация публичных элементов Go должны быть на английском языке. Документировать экспортируемые типы и функции; добавлять комментарии к реализации только для пояснения неочевидного поведения.

## 6. Обработка ошибок, безопасность и ресурсы

- Возвращать ошибки и явно их обрабатывать. Не игнорировать ошибки и не использовать `panic` в производственных сценариях.
- Ограничивать сетевые операции тайм-аутами или отменой, а размер входных данных, параллелизм и потребление других ресурсов — установленными пределами.
- Считать сетевые данные, ввод CLI и конфигурацию недоверенными. Проверять адреса, порты, поля устройств, пароли и значения протокола до использования.
- Разбирать XML с помощью `encoding/xml`; не формировать XML или JSON форматированием строк, если подходит сериализатор.
- Не записывать в журналы пароли, производные от паролей секреты и другие чувствительные данные активации.
- Закрывать файлы, тела HTTP-ответов, сокеты и другие принадлежащие приложению ресурсы на всех соответствующих путях выполнения.

## 7. Требования к спецификациям и проверке

Изменения выполняются согласно [руководству по разработке](../DEVELOPMENT_GUIDE.md):

1. До реализации определить поведение, границы пакетов, типы Go и контракт ошибок.
2. При изменении ответственности или зависимостей модулей обновить этот документ; API пакетов и атомарные процедуры описывать на соответствующих уровнях.
3. Если русская спецификация ссылается на английский контракт, английский документ является нормативным источником; русская версия служит поясняющим указателем и не должна ему противоречить.
4. До написания кода проверить поток данных, обработку ошибок, поддержку платформ, сериализацию, использование контекста и параллелизм.
5. Создавать тесты на основе спецификации: контрактные, позитивные, негативные тесты, проверки тайм-аутов и фаззинг, где он уместен. Файлы Go-тестов должны иметь суффикс `*_test.go`; использовать стандартный пакет `testing`.
6. Выполнить применимые проверки проекта, включая `gofmt`, `go vet ./...`, `go test ./...` и `go build ./...`. Если настроены `staticcheck` или `golangci-lint`, запускать и их.
7. Если реализация меняет описанное поведение, одновременно обновить спецификацию и тесты.

## 8. Python-референс и условия совместимости протокола

Пользователь указал `../examples/SADP-app` как рабочую реализацию на Python и поручил использовать её подход к обработке как локальный поведенческий референс. Реализация использует UDP multicast с выбором интерфейса, передаёт полученные датаграммы с адресом отправителя и временем приёма, разбирает XML в типизированную модель устройства и вычисляет SHA-256 от `UTF-8(password + challenge)` в виде шестнадцатеричной строки нижнего регистра.

Это референс реализации, а не авторитетная спецификация SADP. В имеющихся файлах Python определена только часть сетевого поведения:

- `core/contracts.py` задаёт `239.255.255.250:37020` и `MAX_PACKET_SIZE = 1500`. Размер указан как ограничение для fuzzing/MTU, а не подтверждённый максимум SADP.
- `core/adapter.py` в Unix-подобной ветке присоединяется к multicast-группе на выбранном интерфейсе и привязывает сокет к UDP/37020. Ветка Windows привязывает интерфейсный адрес к эфемерному порту и не присоединяется к группе; реализация Go не должна копировать это расхождение.
- `core/protocol.py` ограничивает размер принимаемых датаграмм и синхронно вызывает обработчик. Явной отправки discovery-запроса, полного обмена запрос/ответ и сопоставления ответов в этих файлах нет.
- `services/parser.py` ожидает прямые дочерние XML-поля `MAC`, `IPv4Address`, `Activated`, `DeviceModel`, `SerialNumber` и необязательное `SoftwareVersion`. Декодирование выполняется как UTF-8 с запасным ISO-8859-1; используется `defusedxml`.
- `services/logic/crypto.py` вычисляет SHA-256 от UTF-8 байтов `password + challenge`. Извлечение `Challenge`/`Salt` само по себе не реализует получение вызова или переговорный обмен.
- `services/logic/__init__.py` формирует XML-запросы `Activate` и `NetworkParameter`. При отсутствии вызова код отправляет пароль открытым текстом; эта резервная ветка не принимается спецификацией Go.

Эти наблюдения можно использовать для реализации и тестовых фикстур, но нельзя выдавать за независимо подтверждённые свойства протокола. До заявления о совместимости необходимо:

- Установить фактическую последовательность discovery и поддерживаемые варианты SADP по сквозному поведению либо воспроизводимым захватам устройств.
- Определить и проверить контракт передачи XML активации и настройки сети: адрес назначения, отправку команд управления, получение/сопоставление ответа, тайм-ауты, отмену и преобразование результата для каждого устройства. M1 отправляет discovery inquiry-probe и принимает датаграммы, но не отправляет команды управления устройствами; одного XML-билдера M3 недостаточно для выполнения операции.
- Сверить XML активации/настройки сети, источник и сопоставление вызова, а также SHA-256 с эталонным обменом. Нельзя считать формулу из Python подходящей для всех моделей и прошивок.
- Если выбран лимит 1500 байт, назвать его ограничением совместимости/ресурсов, а не максимумом протокола; M1 и M2 должны совместно применять один лимит, обнаруживать усечение и отклонять большие датаграммы.
- Проверить привязку UDP multicast к интерфейсам и отмену/освобождение ресурсов на каждой ОС. В частности, не воспроизводить неподтверждённую Windows-ветку Python.
- Окончательно определить пути пакетов. Путь модуля задан в `go.mod`; сигнатуры в спецификациях модулей являются проектными контрактами, а не реализованными символами.

Репозиторий пока не содержит реализации Go. Начать её можно с обработки по границам Python-референса, но совместимость протокола остаётся **неподтверждённой** до выполнения перечисленных проверок.
