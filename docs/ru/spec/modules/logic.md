# Спецификация модуля: M3 — Логика устройств

## 1. Назначение

Реализовывать правила управления устройствами для активации и настройки сети. Модуль проверяет запросы, формирует протокольные сообщения, координирует операции и преобразует ответы устройств в явные результаты.

## 2. Обязанности

- Проверять учётные данные для активации и сетевую конфигурацию до создания команд.
- Формировать SADP XML с помощью типизированных структур Go и `encoding/xml`.
- Координировать обмен «вызов — ответ» и сопоставление команд с результатами, если этого требует протокол устройства.
- Не связывать правила рабочих процессов с отображением CLI и платформозависимой настройкой сокетов.
- Возвращать отдельный результат для каждого устройства при пакетной обработке, чтобы сбои можно было связать с конкретными целями.

Точный алгоритм обмена «вызов — ответ» и поля сетевого протокола должны быть определены в соответствующих спецификациях процедур; эта спецификация модуля не предписывает неподтверждённый алгоритм хеширования.

В M1 определены отправка inquiry-probe и приём датаграмм. XML-билдеры этого модуля сами по себе не образуют сквозные операции активации и настройки сети: для них необходимы проверенный транспортный контракт отправки команд управления/получения ответов и API рабочих процессов с поддержкой контекста.

Локальный Python-референс задаёт поведенческое предложение: XML `Activate` содержит `TargetMAC`, `Password` и необязательный `OptionData/SecurityEmail`; XML `NetworkParameter` содержит `TargetMAC`, `DHCP`, необязательные поля статического адреса и `SecurityResponse` при наличии вызова. Ответ вычисляется как SHA-256 от UTF-8 `password + challenge`. Эти формы полезны для fixtures совместимости, но не являются авторитетными фактами протокола без проверки по обмену с устройством.

## 3. Контракт API Go

Следующие сигнатуры описывают контракт модуля; конкретные пути пакетов и экспортируемые имена будут окончательно определены при реализации:

```go
type ActivationRequest struct {
    MAC      net.HardwareAddr
    Password string
    Email    string
}

type NetworkConfig struct {
    Address netip.Prefix
    Gateway netip.Addr
    UseDHCP bool
}

func ValidatePassword(password string) error
func BuildActivationXML(request ActivationRequest) ([]byte, error)
func BuildNetworkXML(
    mac net.HardwareAddr,
    config NetworkConfig,
    challenge string,
    password string,
) ([]byte, error)
```

- Функции проверки возвращают `nil` только при соответствии входных данных описанным правилам; для некорректных значений возвращаются понятные ошибки, доступные для проверки.
- XML-билдеры проверяют все входные данные и возвращают сериализованные UTF-8 XML-байты или ошибку. При сбое нельзя возвращать частично пригодное сообщение.
- Для статической конфигурации `Address` должен содержать корректный IPv4-адрес и префикс; заданный `Gateway` должен быть корректным IPv4-адресом. При DHCP поля статического адреса и шлюза должны быть пустыми. Некорректные и противоречивые сочетания считаются ошибками.
- `BuildNetworkXML` получает MAC целевого устройства и параметры безопасности отдельно от сетевой конфигурации; он должен использовать описанный в связанных процедурах механизм «вызов — ответ» и не должен незаметно переходить на отправку пароля открытым текстом.
- API операций должны принимать `context.Context`, если выполняют сетевой ввод-вывод или другие блокирующие операции, и возвращать результат либо ошибку для каждого целевого устройства.

## 4. Политика безопасности и ошибок

- Не записывать в журналы пароли, производные секреты, значения вызова и полные сообщения активации.
- Ограничивать область и время жизни учётных данных рамками операции. Строки Go нельзя надёжно стереть из памяти, поэтому нельзя обещать их безопасное обнуление.
- Не встраивать секреты протокола и не предполагать алгоритм хеширования или вычисления ответа без подтверждения спецификацией протокола.
- Возвращать ошибки с контекстом операции и устройства, не раскрывая учётные данные. Сохранять исходные ошибки при оборачивании.
- Не использовать `panic` для неверных запросов, отказов устройства или сбоев транспорта.
- Не копировать fallback Python-референса, который при отсутствии вызова вставляет пароль открытым текстом в XML сетевой настройки. Без вызова операция завершается ошибкой, пока отдельно не будет обоснован и одобрен специальный режим совместимости.

## 5. Требования к тестированию

- Проверять граничные значения политики паролей и некорректные сетевые конфигурации.
- Сверять имена и регистр XML-элементов, экранирование, кодировку и поведение необязательных полей с протокольными примерами.
- Проверять успешные и отклонённые ответы устройств, тайм-ауты, отмену и результаты пакетных операций для каждого устройства.
- Использовать детерминированные тестовые данные; не включать в тесты реальные учётные данные или секреты.
