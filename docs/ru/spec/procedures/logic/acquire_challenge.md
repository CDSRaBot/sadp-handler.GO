# Спецификация процедуры: P3.6 — AcquireChallenge
## Модуль: M3 — Логика устройств

## 1. Назначение

Получить challenge для одной цели мутации и вернуть конечное значение,
ограниченное этой целью и пригодное для последующего запроса настройки сети.

Получение challenge — граница workflow, а не функция хеширования. Точные
wire-поля и допустимые кодировки должны следовать из утверждённых fixture
устройств. Запрещено выводить имя поля, значение статуса или ответ об успехе
из недокументированного перехвата.

Endpoint’ы ISAPI для управления SADP терминала в
`/ISAPI/Publish/TerminalMgr/terminals/discovery` не определяют обмен
challenge в raw SADP UDP. Их документированный ответ при ошибке —
`XML_ResponseStatus`; его нельзя считать ответом challenge. Поток ISAPI
`/ISAPI/Security/challenge` является отдельной HTTP-процедурой безопасности,
а не fixture SADP-датаграммы.

Для управления терминалом через ISAPI грамматика утверждённых ответов может
использовать поля `ResponseStatus` и документированные функциональные коды:
`0x01400004` (`notActivated`), `0x01400005` (`hasActivated`),
`0x01400006` (`forbiddenIP`) и `0x01400007`
(`bondMacAddressNotMatch`). Это состояния устройства/авторизации, а не
значения challenge.

## 2. Контракт Go

```go
type MutationTarget struct {
    MAC    net.HardwareAddr
    Sender net.Addr
}

type Challenge struct {
    Value     string
    TargetMAC net.HardwareAddr
    Sender    net.Addr
    ExpiresAt time.Time
}

type ChallengeProvider interface {
    Acquire(context.Context, MutationTarget) (Challenge, error)
}
```

- До использования транспорта отклонять nil-контекст и неверную либо
  неполную цель.
- Получать challenge через внедрённый транспорт мутаций M1; не открывать
  сокеты и не создавать глобальные клиенты внутри процедуры.
- Проверять ответ по грамматике утверждённых fixture challenge.
- Требовать непустой challenge, запрошенный MAC цели, сопоставленного
  отправителя и срок действия позже времени получения.
- Не возвращать просроченный, несвязанный с целью, неоднозначный или
  несопоставленный challenge.
- Не раскрывать исходные данные ответа в ошибке или сводке challenge.

## 3. Контракт ошибок

Возвращать `DeviceOperationError` со стабильными типами:

- `invalid_input` — неверная цель;
- `transport` — ошибка обмена без более точной классификации;
- `timeout` — истёк deadline;
- `canceled` — контекст отменён;
- `malformed_response` — байты не соответствуют грамматике утверждённых
  fixture;
- `missing_data` — ответ принят, но пригодный challenge отсутствует;
- `response_mismatch` — не совпали отправитель или цель;
- `device_rejected` — устройство явно отклонило получение challenge.

Сохранять исходную причину через `Unwrap`. Ошибки содержат только операцию,
идентичность цели и безопасную категорию сбоя; в них не должны попадать
challenge, пароль, хеш, XML или исходный ответ.

## 4. Требования к обработке

1. Проверить цель и контекст.
2. Запросить один challenge через M1 P1.6.
3. Разобрать ответ по грамматике утверждённых fixture.
4. Проверить корреляцию отправителя и цели.
5. Проверить непустое значение и конечный срок действия.
6. Вернуть challenge только владеющему workflow.

Значения challenge ограничены одной операцией: их нельзя кэшировать
глобально или повторно использовать для другой цели. При ошибке или отмене
пригодный challenge не возвращается.

## 5. Требования к проверкам

Тесты должны охватывать успех, явный отказ, отсутствие challenge,
повреждённый ответ, истёкший срок, несовпадение отправителя и цели,
тайм-аут, отмену, дублирующий ответ и редактирование секретов. Fixture
содержат только синтетические значения.
