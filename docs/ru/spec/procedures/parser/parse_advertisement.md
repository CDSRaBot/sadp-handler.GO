# Спецификация процедуры: P2.1 — ParseAdvertisement
## Модуль: M2 — Парсер данных

## 1. Назначение

Разобрать одно SADP XML-объявление, полученное по UDP, и вернуть типизированную проверенную модель устройства.

## 2. Контракт Go

```go
func ParseAdvertisement(data []byte, sender net.Addr) (Device, error)
```

`Device` — типизированная модель M2, содержащая проверенные MAC- и IPv4-адреса, состояние активации, модель, серийный номер и адрес отправителя.

- Возвращать ошибку для пустой датаграммы, датаграммы размером более общего `MaxSADPDatagramSize` или nil-адреса отправителя. Лимит необходимо проверить по требованиям протокола SADP; нельзя выводить его из MTU Ethernet.
- Возвращать заполненный `Device` и nil-ошибку только при корректности XML и всех обязательных полей.
- При некорректном XML, отсутствии обязательных полей или неверных значениях возвращать ошибку и непригодную для использования модель.
- Эта процедура не записывает ошибки в журнал и не подавляет их. M1 или уровень приложения решает, как сообщать о некорректном сетевом трафике.

## 3. Требования к обработке

1. До разбора ограничить размер проверенным `MaxSADPDatagramSize`; не включать исходное содержимое пакета в диагностику.
2. Разбирать XML непосредственно из байтов с помощью `encoding/xml`. Требовать корректную UTF-8-кодировку, заданную форматом SADP; не переинтерпретировать незаметно некорректные байты в другой кодировке.
3. Отклонять некорректный XML, неожиданные данные после документа и директивы XML, не разрешённые форматом SADP. Ограничивать разбор установленным размером входных данных.
4. Извлечь и проверить обязательные поля:
   - `<MAC>`: разобрать с помощью `NormalizeMAC` (P2.2).
   - `<IPv4Address>`: разобрать как IPv4-адрес с помощью `net/netip`.
   - `<Activated>`: принимать только `true` или `false` без учёта регистра.
   - `<DeviceModel>` и `<SerialNumber>`: требовать непустые значения в пределах документированных протоколом ограничений.
5. Сохранить `sender` в модели устройства, чтобы вышестоящие уровни могли проверить соответствие источника и адреса.
6. Игнорировать неизвестные необязательные элементы, если это безопасно; они не должны переопределять обязательные значения или ослаблять их проверку.

## 4. Ошибки и тесты

Ошибки должны указывать поле или этап разбора и сохранять исходную причину, не включая полную датаграмму или чувствительные данные. Парсер не должен вызывать панику на произвольном вводе.

Тесты должны охватывать корректные объявления, некорректный и усечённый XML, неверный UTF-8, директивы, данные после документа, отсутствующие и неверные поля, сохранение адреса отправителя, точные границы проверенного лимита, неизвестные элементы и Go-фаззинг произвольных срезов байтов.
