# Спецификация процедуры: P1.6 — MutationTransport.Exchange
## Модуль: M1 — Сетевое ядро

## 1. Назначение

Получить ограниченный ответ на уже сформированный SADP payload управления
для одной операции, сохранив метаданные отправителя и владение транспортом.
Эта процедура не интерпретирует ответ.

## 2. Контракт Go

```go
type MutationTarget struct {
    MAC    net.HardwareAddr
    Sender net.Addr
}

type MutationExchange struct {
    Sender net.Addr
    Data   []byte
}

type MutationTransport interface {
    Exchange(context.Context, MutationTarget, []byte) (MutationExchange, error)
}
```

- До открытия сокета отклонять nil-контекст, неверную цель, nil-отправителя,
  если он требуется, пустой payload и payload, превышающий настроенный лимит
  датаграммы.
- Требовать конечный deadline, переданный вызывающей стороной, либо явно
  заданный конфигурацией M1 транспортный тайм-аут по умолчанию. Отмена должна
  прерывать каждую блокирующую операцию.
- Отправлять ровно один payload за один обмен. Повторы не входят в эту
  процедуру и не могут добавляться неявно.
- Возвращать полученные байты и фактический адрес отправителя без разбора и
  нормализации. Проверка ответа принадлежит вызывающей стороне.
- Ограничивать размер ответа. Превышение лимита — типизированный транспортный
  сбой, а не успешный усечённый ответ.

## 3. Владение ресурсами и контракт ошибок

Транспорт владеет созданными им соединениями и закрывает их при любом
исходе. Соединение, принадлежащее вызывающему коду, остаётся в его владении;
транспорт сериализует использование обмена и документирует требуемое владение
reader/writer. Ошибка закрытия возвращается и не скрывает более раннюю
транспортную ошибку.

Сбои используют контракт транспортных ошибок M1 и сохраняют исходные причины:

- `validation` — неверные аргументы;
- `write` или `short_write` — ошибка отправки запроса;
- `read` — ошибка приёма;
- `timeout` — истёк транспортный deadline;
- `canceled` — контекст отменён;
- `response_too_large` — превышен лимит размера;
- `close` — очистка завершилась ошибкой при отсутствии более раннего сбоя.

Сообщения ошибок содержат только этап операции, размеры и безопасные сведения
об endpoint. В них не должно быть байтов payload, XML, паролей, challenge
или хешей.

## 4. Требования к обработке

1. Проверить цель, payload, лимит и контекст.
2. Установить документированный deadline и владение ресурсами.
3. Отправить одну датаграмму.
4. Прочитать один ответ ограниченного размера и сохранить его отправителя.
5. Передать ответ в M3 для извлечения challenge или разбора результата
   мутации.
6. Закрыть принадлежащие транспорту ресурсы и вернуть ошибку очистки согласно
   контракту транспортных ошибок.

Адрес отправителя намеренно не обязан совпадать с целью на этом уровне. M1
сохраняет его, а M3 выполняет корреляцию для конкретной операции.

## 5. Требования к проверкам

Тесты по этой процедуре используют детерминированные фальшивые соединения и
покрывают проверку входа, одну запись, короткую запись, ограниченное чтение,
чрезмерный ответ, сохранение отправителя, deadline, отмену и ошибки закрытия.
Реальное устройство или multicast-сеть не требуются.
