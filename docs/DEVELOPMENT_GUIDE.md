# Руководство по циклу разработки (Development Lifecycle Guide)
## Проект: SADP-handler
## Язык: Go
## Версия: 1.0.0

Данный документ устанавливает обязательный порядок выполнения работ по расширению или модификации системы на Go. Принцип: **«Проектирование важнее кода»**.

---

## Фаза 1: Определение задачи (Task Definition)
Каждая фича начинается с четкого описания цели и технического контракта.
- **Результат**: определение границ ответственности, поведения, внешнего API и допустимых входных/выходных данных.
- **Для Go**: фиксируются:
  - пакеты и публичные функции;
  - типы данных и структуры;
  - ожидаемые ошибки и их значения;
  - контракт взаимодействия с сетью, XML, HTTP, UDP, файлами и CLI.

## Фаза 2: Декомпозиция (Top-Down Specification)
Движение от общего к частному по уровням:
1. **Уровень системы (`SYSTEM.md`)**:
   - регистрация нового модуля;
   - описание его роли в приложении;
   - границы ответственности и зависимостей.
2. **Уровень пакета (`internal/...`, `pkg/...`)**:
   - назначение пакета;
   - публичный API;
   - входные и выходные структуры;
   - ограничения по производительности и обработке ошибок.
3. **Уровень функции / метода (`procedures/*.md`)**:
   - атомарное описание логики;
   - обязательный контракт:
     - входные параметры;
     - возвращаемые значения;
     - типы ошибок;
     - поведение на nil / пустых данных / таймаутах;
   - обязательный список исключений (`errors` / `panic` policy).

## Фаза 3: Рекурсивный аудит спецификаций (Spec Audit)
Перед написанием кода проверяется целостность документации:
- **Цепочка данных**: вывод функции N должен полностью покрывать входные требования функции N+1.
- **Модель ошибок**: каждый возможный сбой описан и имеет обработку.
- **Кроссплатформенность**: проверка, что все используемые системные вызовы, сетевые операции и пути файлов поддерживаются на целевых ОС.
- **Go-спец**:
  - проверка корректности типов (`struct`, `interface`, `error`);
  - проверка корректности использования `context.Context`;
  - проверка сериализации/десериализации JSON/XML;
  - проверка корректности `goroutine` и `channel`-схемы, если используется конкурентность.

## Фаза 4: Написание тестов (Test-Driven Development)
Создание тестов на основе спецификаций до написания кода.
- **Контрактные тесты**:
  - проверка типов данных;
  - проверка структур и полей;
  - проверка возврата ошибок.
- **Логические тесты**:
  - проверка алгоритмов на эталонных данных;
  - проверка XML/JSON парсинга;
  - проверка сетевых сценариев.
- **Негативные тесты**:
  - обработка пустых входов;
  - неверный XML;
  - неполные структуры;
  - таймауты;
  - некорректный формат данных;
  - fuzzing для строк и бинарных данных.
- **Go-стиль**:
  - тесты находятся в файлах `*_test.go`;
  - используются `testing` и `t.Run`;
  - проверка ошибок через `require`/`assert` или стандартный `testing`.

## Фаза 5: Реализация (Bottom-Up Coding)
Написание кода от самых мелких атомарных функций к точкам входа.
- Собирать проект по правилам Go:
  - пакетный нейминг;
  - понятные имена функций;
  - отсутствие глобального состояния без необходимости;
  - явная обработка ошибок;
  - использование `context.Context` в сетевых и I/O-операциях.
- **Стандарты документирования**:
  - комментарии и docstrings на английском языке;
  - описание публичных функций и типов;
  - комментарии только там, где это реально помогает.
- **Обязательные правила**:
  - не использовать `panic` в production-логике;
  - не игнорировать `error`;
  - не использовать `fmt.Sprintf` для сборки XML/JSON без необходимости;
  - избегать утечек goroutines;
  - закрывать ресурсы: `defer file.Close()`, `defer resp.Body.Close()`.

## Фаза 6: Рекурсивная валидация кода
Процесс проверки соответствия кода и спецификации:
1. **Unit-проверка**: каждая функция проходит свой тест.
2. **Chain-проверка**: проверка корректной трансформации данных между пакетами и уровнями приложения.
3. **Integration-проверка**: проверка взаимодействия с сетью, XML, HTTP, устройствами и файлами.
4. **Refactoring**: если код потребовал изменения логики, возвращаемся к Фазе 2 и правим спецификацию.

## Фаза 7: Статический анализ и QA (Linting)
Запуск инструментов контроля качества:
- `gofmt -w .` — форматирование кода;
- `go vet ./...` — поиск типичных ошибок Go;
- `staticcheck ./...` — статический анализ;
- `golangci-lint run` — единая проверка качества;
- `go test ./...` — запуск всех тестов;
- `go mod tidy` — актуализация зависимостей;
- `go build ./...` — проверка сборки проекта.

## Фаза 8: Сборка, релиз и версионирование
1. **Тестирование**:
   - все unit/integration тесты зелёные;
   - сборка без ошибок.
2. **Commit**:
   - фиксация изменений;
   - подробное описание в commit message.
3. **Tag**:
   - создание Git-тега для версии проекта;
   - предпочтительно использовать `vX.Y.Z`.
4. **Push**:
   - синхронизация с удаленным репозиторием.
5. **Release**:
   - подготовка changelog;
   - фиксация релиза и бинарных сборок при необходимости.

## Фаза 9: Архитектурные правила Go-проекта
Для всех изменений в проекте соблюдаются следующие принципы:
- **`cmd/`** — точка входа приложения;
- **`internal/`** — бизнес-логика и приватные компоненты;
- **`pkg/`** — переиспользуемые библиотеки, которые могут быть вынесены наружу;
- **`config/`** — параметры конфигурации;
- **`models/`** — структуры данных;
- **`utils/`** — вспомогательные функции;
- **`docs/`** — документация и спецификации.
- Не смешивать уровни ответственности.
- Не использовать глобальные переменные без крайней необходимости.
- Использовать интерфейсы там, где требуется тестируемость и замена зависимостей.
- Сохранять логику работы с устройствами, XML и сетью в отдельных пакетах.

## Фаза 10: Политика ошибок и безопасности
- Все ошибки должны быть явными и проверяемыми.
- Не использовать `panic` в рабочем коде, кроме `main` и явно ограниченных сценариев.
- Сетевые запросы должны иметь таймауты.
- XML/JSON должны валидироваться и корректно обрабатываться.
- Ограничивать размер входных данных и количество ресурсов.
- Не доверять входным данным без проверки.
